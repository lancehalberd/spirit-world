# Audio synthesis architecture

Companion to [CLAUDE.md](../CLAUDE.md). Covers the Web Audio-based instrument/music-track system under `app/utils/instruments/` and `app/utils/music/` — synthesizing individual notes and sequencing them into tracks, as opposed to the pre-rendered mp3 `GameTrack`s in `app/utils/sounds.ts`.

## Instrument system
- `app/utils/instruments/instrumentHash.ts` — registry (`instruments[name]`) + the `Instrument`/`InstrumentPlayNoteParams`/`InstrumentName` global types. Same registry pattern as `objectHash` etc: each `app/utils/instruments/*.ts` file assigns itself in at module-load time.
- `app/utils/instruments/instrumentPlayer.ts` — `playNote({instrument, noteOrFrequency, time, duration, volume, destination})`, the single entry point everything else (manual console calls, the music track scheduler) goes through. Resolves a `Note` name via `noteFrequencies` (`app/utils/noteFrequencies.ts`) or accepts a raw frequency.
- `app/utils/instruments/noiseBuffer.ts` — shared white-noise `AudioBuffer` for percussion instruments (snare, hihat). See "Noise" below for why this exists instead of reusing `app/utils/sounds.ts`'s pink/white noise AudioWorklet nodes.
- Current instruments: `bell`, `harp`, `hihat`, `zeldaSquare`, `kick`, `snare`, `bass`. Each file documents the sources that were actually useful for tuning it — check there before re-deriving a technique from scratch.
- `app/utils/instruments/waveformGain.ts` — `getWaveformGain(oscillatorType)`, a per-waveform gain-compensation factor (sine 1, triangle 0.9, sawtooth 0.6, square 0.5) applied wherever an instrument creates an oscillator directly (`bass.ts`, `snare.ts`'s body tone) or via `playSimpleSound` (`zeldaSquare`), so `volume` means roughly the same perceived loudness regardless of waveform. These are theory-derived starting points (see "Loudness normalization" below), not final numbers — re-tune by ear as instruments are compared. `kick`/`bell`/`harp` are pure sine and need no compensation (factor 1); `hihat`/`snare`'s noise layer is broadband, not a periodic waveform, so the table doesn't apply there.

## Music track system
- `app/utils/music/musicTrackHash.ts` — data model: `MusicTrackDefinition` (bpm, parts, optional loop range) → `MusicPart` (instrument + notes, plus optional `note`/`frequency`/`beats`/`duration` defaults) → `NoteEvent` (beat offset, note/frequency, beats/duration, volume). Beats are quarter notes; a note's `beat` is relative to the start of its part. Chords are just multiple `NoteEvent`s sharing a `beat`.
  - `note` (a `Note` name) and `frequency` (raw Hz) are separate, mutually-exclusive fields - resolved as `note.note ?? note.frequency ?? part.note ?? part.frequency`, so a part can set a default pitch once (e.g. the kick/hihat parts in `bossTheme.ts`) and individual notes only need `{beat: N}`.
  - Likewise `beats` (length in quarter-note beats) and `duration` (length in seconds) are resolved per-note-then-per-part, falling back to one beat's worth of seconds if nothing is set. `duration` in seconds is useful for instruments whose natural length shouldn't scale with tempo (e.g. a hihat's transient).
- `app/utils/music/musicTrackPlayer.ts` — `playMusicTrack(key, {fadeDuration})` / `stopMusicTrack(fadeDuration)` / `updateMusicTrackPlayback()`. Uses the standard lookahead-scheduler technique (schedules ~200ms ahead of `audioContext.currentTime` rather than trusting JS timer precision); driven once per frame from `app/client.ts`'s render loop, alongside `updateMusic(state)`.
- Crossfading: each `playMusicTrack` call gets its own `GainNode` (feeding into the shared `trackGainNode` bus from `app/utils/sounds.ts`), so an outgoing and incoming track can ramp independently and overlap during a transition instead of sharing one gain.
- Looping: `loopStartBeat`/`loopEndBeat` mark a range that repeats indefinitely once reached, so anything before `loopStartBeat` plays once as an intro. Mirrors the existing `nextTrack`-chaining pattern used for the mp3 boss music (`bossIntro → bossA → bossB → bossA` in `app/utils/sounds.ts`).
  - `loopEndBeat`, when not set explicitly, is computed by `getTrackEndBeat` as the smallest whole number of beats containing every note's *start* beat - deliberately ignoring note length entirely. A note is free to ring out past the loop point (it's already been scheduled with its own `.stop()` time, independent of the loop's bookkeeping) without forcing the loop itself to be any longer. Don't "fix" this to factor in `beat + duration` again - that was tried and reverted on purpose.
- `app/content/music/*.ts` — hand-authored tracks, self-registering into `musicTrackHash`, same pattern as zone files registering into `zones`.

## Synthesis notes (learned the hard way)
- **Verify against a known recipe, don't design from theory alone.** Nobody in this loop can actually hear the output while writing the code, so "this seems like it should sound right" is not a reliable check. Look up how a real (or well-documented software) instrument of the same kind is actually built, then implement *that*, and check the implementation against the recipe rather than against your own ear.
- **A drum's "click"/transient is usually just its main envelope, not an extra layer.** A kick's click comes from how fast its pitch envelope decays (~20-70ms), not from a second oscillator playing at the same time. Layering an unrelated tone on top for "attack" tends to just sound like two colliding pitches (harsh/metallic) rather than a transient.
- **Percussion "noise" needs to actually be noise.** A stack of detuned oscillators (even at inharmonic ratios) is still periodic and reads as buzzy/metallic, not broadband. Use `noiseBuffer.ts`'s shared `AudioBuffer` of random samples through a highpass/bandpass filter instead. (The project's existing `pinkNoiseNode`/`whiteNoiseNode` in `app/utils/sounds.ts` are AudioWorklet nodes that load asynchronously and aren't exported outside that file — a plain buffer sidesteps both issues and is generated synchronously.)
- **Randomize noise playback offset.** Reading a noise buffer from the same start point every time makes repeated short hits (e.g. a run of hihat eighth notes) sound identical/phasey. `getRandomNoiseOffset()` picks a random start point per hit.

## Loudness normalization
Different instruments read as louder or quieter than each other at the same nominal `volume`, for reasons unrelated to how many oscillators they use:
- **Waveform shape** dominates: a square wave's RMS equals its peak (crest factor 1) vs. a sine's ~0.707x-of-peak RMS, and perceived loudness gaps run even wider than that ~3dB RMS difference because extra harmonic energy engages more of the ear's loudness response. This is why `zeldaSquare` (one square oscillator) reads louder than instruments built from sine/triangle voices - "one oscillator" isn't "one unit of loudness." `waveformGain.ts` compensates for this with per-waveform-type factors.
- **Pitch** matters too, separately: human hearing is measurably less sensitive to low frequencies than to ~500Hz-4kHz (equal-loudness contours / Fletcher-Munson), so a bass note and a lead note at identical gain won't sound equally loud. Not yet compensated for here - a literal equal-loudness contour can demand tens of dB of bass boost at low levels, which risks clipping the low end, so this needs a deliberately capped approach if it's ever tackled rather than the textbook curve.
- Per-instrument envelope/filtering/overtone-stacking differences aren't captured by the waveform table at all (e.g. bell/harp's decaying overtone stack already self-normalizes somewhat) - closing that gap needs listening and a per-instrument trim, not more research.
- Calibration method used here: play every instrument back-to-back at the same note/volume/duration (`playNote({instrument, noteOrFrequency: 'A4', volume: 0.5, duration: 0.5})`) and compare by ear against a reference (a sine-based instrument), rather than trying to derive exact numbers analytically.

## Gotchas
- Instruments only receive a `frequency`, not a semantic "this is percussion" flag — percussion instruments (kick/snare/hihat) just treat it as a base pitch to derive their internal ratios/cutoffs from, which is why note choice still has an audible (if secondary) effect on them.
- `playMusicTrack`/`stopMusicTrack` no-op if the requested track is already the active, non-fading one — safe to call every frame the way `updateMusic` already does with `playTrack`.
- **`AudioParam.value = x` is not "harmless immediate assignment" - it's `setValueAtTime(x, audioContext.currentTime)`, timestamped at the moment the JS runs.** Because the lookahead scheduler schedules notes up to `SCHEDULE_AHEAD_TIME` ahead of when they'll actually play, that execution moment is normally *earlier* than the note's own `time`. A later `linearRampToValueAtTime`/`exponentialRampToValueAtTime` ramps from whichever prior automation event has the latest timestamp - so if you only ever set `.value = volume` and then ramp, the ramp's real anchor is that too-early "now" event, and the fade will already be partway (or all the way) decayed before the note is even meant to start. Fix: schedule an explicit `setValueAtTime(volume, time)` (see `hihat.ts`) to pin the ramp's actual start; don't assume `.value =` alone is enough once a `time` in the future is involved.
- **Waveform type changes perceived loudness independent of the `volume` you pass.** A square wave's RMS equals its peak (crest factor 1); a sine wave's RMS is ~0.707x its peak - so a square oscillator is inherently louder than a sine at the same nominal gain, and real-world reports put the *perceived* gap even wider than the ~3dB RMS difference alone, because the extra harmonic energy engages more of the ear's loudness response. This is why `zeldaSquare` (a single square oscillator) reads louder than instruments built from sine/triangle voices or a sum of several oscillators - "one oscillator" doesn't mean "one unit of loudness." See "Loudness normalization" above for how instruments compensate for this.
